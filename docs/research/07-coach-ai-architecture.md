# 07. Архитектура AI-тренера, «заземлённого» на движок: prior art и проект

Версии, звёзды и лицензии — по `npm view` и `gh api`; формулы и пороги — по исходному коду lichess/Chesskit; цены и API — по документации OpenAI (всё по состоянию на 2026-09-21). То, что проверить не удалось, помечено «не проверено».

---

## 0. Главные выводы (TL;DR)

1. **Единственный надёжный принцип: «движок решает, код доказывает, LLM пересказывает».** LLM (в том числе фронтир-модели 2026 года) нельзя просить «посмотреть на позицию и объяснить». Свежий бенчмарк ACT-Eval (arXiv 2608.04240, август 2026): у GPT-5.4 без инструментов **22,0 %** проверяемых утверждений в шахматном комментарии ложные, с инструментами движка — 9,2 %; у моделей поменьше — 40–55 %. ~30 % ошибок — «не так увидел доску», ~35 % — выдуманная тактика. Значит, всё, что можно вычислить детерминированно (кто кого бьёт, что висит, какая вилка, сколько материала), вычисляется **в коде** и передаётся модели как готовые факты, а лучше — как готовые проверенные русские фразы (`talkingPoints`).
2. **Классификация ходов — по шкале Win% lichess**, а не по сантипешкам: `Win% = 50 + 50·(2/(1+exp(−0.00368208·cp)) − 1)`; пороги потери Win%: 2 / 5 / 10 / 20 (Chess.com / Chesskit) или 5 / 10 / 15 (lichess). Для ребёнка-новичка поверх этого нужен **«фильтр объяснимости»**: вмешиваемся только тогда, когда опровержение — конкретное и короткое (висит фигура, мат в 1–2, простая вилка), а не «движок видит −2.0 на глубине 20».
3. **Поток «подожди, верни ход»**: пока ребёнок думает, судейский движок уже анализирует позицию (`go infinite`, MultiPV=3). После хода: если ход в кэше MultiPV — вердикт за 0 мс; иначе быстрый поиск 250 мс + подтверждение 350 мс. Бот не отвечает, пока вердикт не готов (это прячется в его «человеческую» задержку 0,8–2 с). Вмешательство — это **предложение** вернуть ход с лестницей подсказок «вопрос → тема → зона доски → фигура → ход» (в ITS-литературе это Point → Teach → Bottom-out, VanLehn 2006).
4. **Часы**: во время речи тренера часы обеих сторон стоят; после возврата хода часам ребёнка возвращается значение до ошибочного хода. В 1-минутных партиях тренер **никогда** не вмешивается и не говорит — только разбор после партии. Небольшие реплики в 5/10-минутках произносятся «за счёт времени бота».
5. **Голос**: realtime-модель (`gpt-realtime-2.1` / `gpt-realtime-2.1-mini`, вышли 2026-07-06; старое семейство `gpt-realtime` устарело и отключается 2027-01-20) получает не FEN, а компактный `CoachEvent` (≤ 300–400 токенов) через `conversation.item.create` + `response.create`. Для вопросов ребёнка у неё есть локальные инструменты (`explain_move`, `get_hint`, `show_on_board` …), отвечающие за < 300 мс. Задержку до первого звука маскирует локальный заранее записанный клип («Стой-стой!») и анимация маскота. С 2026-09-10 в API есть ещё и **`gpt-live-1`** (Live API, `POST /v1/live/sessions`) — полнодуплексная модель «слушает и говорит одновременно», которую документация OpenAI рекомендует как стартовую для новых голосовых приложений; её режим *client delegation* (`session.commentary.append` — «модель пересказывает переданный текст», `session.thinking.append` — факты «про себя») почти буквально совпадает с нашим принципом «LLM только пересказывает». Цена — $0.05/мин сессии (≈ $3/ч, включая тишину), против по-токенной у `gpt-realtime-2.1`. Голосовой слой надо прятать за интерфейсом `VoiceTransport` и сравнить оба варианта на русском (см. 5.1a).
6. **Подписка vs API**: всё не-реалтаймовое (разбор партии, журнал, план занятий, генерация формулировок) можно гонять через `codex exec --output-schema … --json` на подписке ChatGPT (флаги проверены локально на codex-cli 0.154.0). Realtime/Live API подпиской не покрывается (подтверждено страницей цен Codex: голос GPT-Live на подписке есть только внутри десктоп-приложения ChatGPT и «isn't available via API key») — это единственная обязательная статья расходов по API. Пробный `codex exec --output-schema` вернул `You've hit your usage limit … try again at …` — квота подписки общая со всей остальной работой в Codex и реально заканчивается; кроме того, без явных флагов наследуется пользовательский конфиг, который может указывать самый «дорогой» по квоте вариант (например, `gpt-6-astra` с reasoning effort `ultra`). Поэтому (а) fallback на API обязателен, а не опционален; (б) в вызове явно задавать дешёвую модель и усилие: `-m gpt-5.6-luna` (или `gpt-5.6-terra`) `-c model_reasoning_effort="low"` и `--ignore-user-config`; (в) удобнее не спавнить CLI руками, а взять официальный `@openai/codex-sdk` (см. 3.1, 6.1).
7. **Модель ученика**: темы совместимы с темами пазлов lichess (`fork`, `pin`, `hangingPiece`, `backRankMate` …), по каждой теме отдельно «атака» (увидел свою тактику) и «защита» (не зевнул чужую). Ошибки ребёнка превращаются в карточки-пазлы с расписанием FSRS (`ts-fsrs` 5.4.2, MIT). Так делают Noctie и Aimchess; открытый Arrakis_Engine делает то же для ребёнка + отдельные заметки для родителя.

### 1.3. Что именно делает lichess (прочитан исходный код)

- `scalachess/core/src/main/scala/eval.scala`: `winningChances(cp) = 2/(1+exp(−0.00368208·cp)) − 1`, cp обрезается до ±1000 (`Cp.CEILING`); `WinPercent = 50 + 50·winningChances`. Мат на сервере = ±1000 cp; в UI (`ui/lib/src/ceval/winningChances.ts`) мат-в-N = `(21 − min(10, N))·100` cp.
- Константа получена в PR #11148 (влит 2022-07-09): `curve_fit` по 75k позиций из рапид-партий **2300+**. Автор прямо пишет: *«This value will be closer and closer to −0.002 as the ELO decreases»* (и к −0.0038 при росте рейтинга) — т. е. для новичка та же потеря в cp означает меньшую практическую потерю шансов. Это аргумент не интерпретировать Win% буквально для ребёнка, а добавлять материальный/объяснимый критерий.
- `lila/modules/tree/src/main/Advice.scala`: пороги на шкале winningChances [−1; 1]: **0.1 → Inaccuracy, 0.2 → Mistake, 0.3 → Blunder** (= 5 / 10 / 15 пунктов Win%). Маты: `MateCreated` (позволил форсированный мат): если до этого было < −999 → Inaccuracy, < −700 → Mistake, иначе Blunder; `MateLost` (упустил свой мат): если после хода всё ещё > 999 → Inaccuracy, > 700 → Mistake, иначе Blunder; `MateDelayed` — не наказывается (advice = None).
- `lila/modules/analyse/src/main/AccuracyPercent.scala`: точность хода `103.1668100711649·exp(−0.04354415386753951·ΔWin%) − 3.166924740191411 + 1` (бонус +1 «за неидеальность анализа»), clamp 0..100; точность партии = (**взвешенное по волатильности среднее** + **гармоническое среднее**) / 2; окна размером `(nMoves/10).squeeze(2, 8)`, вес = stddev Win% в окне, clamp 0.5..12.
- «Learn from your mistakes» (`ui/analyse/src/retrospect/retroCtrl.ts`, `nodeFinder.ts`): кандидат = ход со свингом `|povDiff| > 0.1` (povDiff = Δchances/2, т. е. > 10 п. Win%) **или** упущенный мат ≤ 3; ходы из дебютной базы мастеров пропускаются; ответ засчитывается, если это ход движка, мат, ход из дебютной книги или локальный движок показывает `povDiff > −0.04` (потеря < 4 п. Win%); локальная оценка считается готовой при `bestmove ‖ nodes ≥ 1_000_000 ‖ millis > 3000`.
- Режим «показать угрозу» (`ui/lib/src/ceval/ctrl.ts`): в FEN переворачивается очередь хода (`fields[1]`) и стирается поле en passant (`fields[3] = '-'`) — это и есть null-move поиск угроз, проверенный в проде.
- Критерий неоднозначности пазла: вторая линия «слишком хороша», если её шансы ≥ 0.3524 (ровно +200 cp) или `povDiff(best, second) < 0.14` (`areSimilarEvals`).

## 2. Классификация ходов

### 2.1. Формулы (эталон — lichess)

```ts
// POV: всегда с точки зрения того, кто сделал ход
export type Score = { kind: 'cp'; value: number } | { kind: 'mate'; value: number }; // mate>0: мы матуем за N ходов

const K = 0.00368208; // lichess PR #11148; для новичков практическая кривая положе (~0.002), см. 1.3

export function winPct(s: Score): number {
  const cp = s.kind === 'cp'
    ? Math.max(-1000, Math.min(1000, s.value))
    : Math.sign(s.value) * (21 - Math.min(10, Math.abs(s.value))) * 100; // как в lichess UI
  return 50 + 50 * (2 / (1 + Math.exp(-K * cp)) - 1);
}

export function moveAccuracy(winBefore: number, winAfter: number): number {
  if (winAfter >= winBefore) return 100;
  const raw = 103.1668100711649 * Math.exp(-0.04354415386753951 * (winBefore - winAfter)) - 3.166924740191411 + 1;
  return Math.max(0, Math.min(100, raw));
}
```

Контрольные значения (посчитаны скриптом и вручную по формуле): cp → Win%: 0 → 50.0; 100 → 59.1; 200 → 67.6; 300 → 75.1; 500 → 86.3; 900 → 96.5; мат в 1 → 99.94.
Потеря 300 cp (фигура) из равной позиции = −25.1 п. Win% (точность хода 32); та же потеря из +6.00 = всего −15.0 п.; потеря 100 cp из +6.00 = −3.8 п. — шкала сама «прощает» неточности в выигранной позиции, в этом её смысл.

### 2.2. Пороги

| Класс | lichess (ΔWin%) | Chess.com (expected points) | Chesskit (ΔWin%) | **Предлагаем (ΔWin%)** |
|---|---|---|---|---|
| best | — | 0 | ход = bestmove | ход = PV[0] или ΔWin < 0.5 |
| excellent | — | ≤ 0.02 | < 2 | < 2 |
| good | — | 0.02–0.05 | 2–5 («Okay») | 2–5 |
| inaccuracy | ≥ 5 | 0.05–0.10 | 5–10 | 5–10 |
| mistake | ≥ 10 | 0.10–0.20 | 10–20 | 10–20 |
| blunder | ≥ 15 | ≥ 0.20 | ≥ 20 | ≥ 20 |
| missedWin («Miss») | упущенный мат ≤ 3 | есть, зависит от рейтинга | — | см. ниже |
| forced | — | — | 1 легальный ход | 1 легальный ход |
| book | пропуск по базе мастеров | Book | по таблице дебютов | по своей мини-книге |
| great / brilliant | — | есть, мягче для новичков | Perfect / Splendid | как в Chesskit |

Дополнительные правила:

- **missedWin**: соперник предыдущим ходом ошибся (Win% ребёнка вырос на ≥ 15 п. или появился мат ≤ 3 / выигрыш ≥ 3 очков материала в ≤ 3 полухода), а ход ребёнка вернул Win% к уровню «до подарка» (потеря ≥ 10 п.), но при этом позиция ребёнка не стала плохой. Для ребёнка это отдельная, **не обидная** категория: «тут был подарок».
- **Маты** — как в `Advice.scala` (MateCreated / MateLost / MateDelayed, см. 1.3).
- **great** (по Chesskit `isPerfectMove`): потеря < 2 п., не простое взятие-отыгрыш, позиция не проиграна, альтернатива не «и так выиграно» (> 97 %), и либо ход переломил партию (> 10 п. через отметку 50 %), либо он единственный хороший (вторая линия хуже на > 10 п.). **brilliant** = то же + жертва фигуры. Это повод для похвалы, для ребёнка критично.

### 2.3. Адаптация к ребёнку-новичку

1. **Внутри** храним полную шкалу (сравнимость с lichess/Chess.com, прогресс точности). **Ребёнку** показываем укрупнённо: «Супер!» (best / great / brilliant), «Хорошо» (excellent / good), «Можно лучше» (inaccuracy — показывать только с уровня T2), «Ошибка», «Зевок», «Упущенный шанс».
2. **Детская серьёзность** (`childSeverity`) — не только ΔWin%, но и *конкретность*: сколько материала теряется и через сколько полуходов, есть ли мат. Новичку ошибка «−1.8 через 9 полуходов» не объяснима и не учит ничему; «конь остался под боем» — учит. Arrakis решает это ослаблением cp-порогов (новичок < 800: blunder ≥ 500 cp, mistake 200–500, inaccuracy 100–200); мы — отдельным полем `explainability` (см. 3.4) плюс материальным критерием.
3. Точность в % ребёнку не показывать (цифра 43 % демотивирует); родителю — показывать, вместе с трендом.
4. Дебют (первые ~8–10 ходов): вместо «неточность −0.4» — флаги дебютных принципов (см. 3.2), потому что новичок учит принципы, а не теорию.

Алгоритм определения причины зевка (детерминированный):

1. `r = refutation.pv[0]`. Если `r` — взятие фигуры X на поле s:
   - X — та фигура, которой ребёнок только что пошёл → `movedIntoAttack` (подвид: `attackedByLower` или «поле не защищено»);
   - X висела уже в позиции **до** хода → `ignoredThreat`;
   - X до хода была защищена, а теперь нет: защитником была ушедшая фигура → `removedOwnDefender`; линия открылась ходом → `openedLine`;
   - ход ребёнка сам был взятием и SEE < 0 → `badTrade`.
2. Если в опровержении мат ≤ N → `allowedMate` + паттерн (backRank, smothered …).
3. Если `r` — не взятие, но детектор мотивов на PV сработал (вилка/связка/сквозной удар) → `walkedInto*`.
4. Для missedWin — то же по лучшей линии: `missedFreeCapture` / `missedMate` / `missedFork` …
5. Иначе → `unknownPositional`, `explainability = 0` → **вживую не вмешиваемся**, только в разборе и только если LLM-разбор сумеет опереться на факты.

### 3.3. Принципы подачи фактов в LLM

- **Не давать голый FEN как единственный источник.** FEN/ASCII-доска — только приложение; основное — перечисленные факты (в CCC в промпт явно перечисляют все атаки; в ACT-Eval 30 % ошибок — неправильное «зрение»).
- **Приоритезация** (идея CCC): в событие кладутся 1–3 факта, которые *изменились* этим ходом, а не полный дамп позиции. Полный дамп доступен через tool.
- **Готовые русские фразы** (`talkingPoints`) из шаблонов: «Твой слон на c4 остался без защиты, и его бьёт пешка b5». Realtime-модель меняет тон, а не содержание. Это же решает проблему произношения ходов: в событии есть `spokenRu` («конь с g1 на f3»), модель не транслирует SAN сама.
- **Белый список упоминаний** (`mentionable`): ходы, поля и фигуры, которые модель вправе назвать в этой реплике. Всё остальное — запрещено системной инструкцией.
- **Уровень уверенности**: `confidence: 'quick'` → тренер говорит мягко («кажется, тут что-то не так, посмотри»), `'confirmed'` → уверенно.

### 3.4. Explainability (0–3)

| Значение | Критерий | Кто понимает |
|---|---|---|
| 3 | опровержение/упущенная возможность в 1 полуход: фигура висит, мат в 1, бесплатное взятие | T0+ |
| 2 | ≤ 3 полухода, один мотив из базовых (вилка, связка, мат в 2, слабость последней горизонтали) | T1+ |
| 1 | ≤ 7 полуходов, любой распознанный мотив или цепочка из двух | T2+ |
| 0 | мотив не распознан / чисто позиционная потеря | только разбор, T3+ |

## 4. Поток «Подожди, верни ход и подумай»

### 4.1. Два движка

- **Bot engine** — ослабленный/человекоподобный (тема другого исследования), играет за Петю/Сашу/Диму.
- **Judge engine** — полный Stockfish 19, отдельный процесс, фиксированные `Threads`/`Hash`; никогда не ждёт бота. Он же считает null-move угрозы и послепартийный анализ.

### 4.2. Конвейер проверки хода

```
Ход бота сделан → позиция P0 (ход ребёнка)
  ├─ judge: go infinite, MultiPV=3 на P0 (идёт всё время, пока ребёнок думает → бесплатная глубина)
  ├─ judge#2 / чередование: null-move угрозы против ребёнка (100–150 мс)
  └─ код: PositionFacts(P0), мотивы лучшего хода, заготовки подсказок L1–L4 (они зависят только от P0!)
Ребёнок отпустил фигуру (t = 0), ход m
  t≈1 мс   легальность (chess.js), stop judge, читаем последние info
  ├─ m ∈ MultiPV-кэш → оценка «после» из той же линии (та же глубина, лучшая согласованность) → вердикт за ~0 мс
  └─ иначе: position P0 moves m → go movetime 250, MultiPV=1 → оценка + PV-опровержение
  t≈250 мс  предварительный MoveJudgement (confidence = 'quick')
  ├─ нет подозрения → бот может ходить (после своей «человеческой» паузы)
  └─ подозрение (порог уровня, см. 4.4) → go movetime +350 (хэш сохранён → поиск инкрементальный)
  t≈600 мс  confirmed: материальная проверка PV проигрыванием на доске (детерминированно) + causes + explainability
  └─ decideIntervention() → либо бот ходит, либо COACH_INTERRUPT
```

Бот в любом случае ждёт `Promise.all([judgement, minBotDelay])`, поэтому ребёнок не замечает проверки. Оценка глубины за 250 мс на одном потоке нативного Stockfish — ориентировочно 14–17 полуходов в миттельшпиле (не проверено, измерить). Этого достаточно для зевков фигур и матов в 2–3, которые только и интересуют нас вживую; от ложных срабатываний из-за разной глубины «до/после» защищают: (а) порог ≥ 15–20 п. Win%, (б) обязательная материальная/матовая конкретика в PV, (в) подтверждающий поиск.

### 4.3. Машина состояний

```
CHILD_TURN ──ход──▶ JUDGING (бот заморожен)
JUDGING ──ok──▶ BOT_THINKING ──▶ BOT_MOVED ──▶ CHILD_TURN
JUDGING ──intervene──▶ COACH_INTERRUPT (часы стоят; ход показан «призраком»; маскот «Стоп!»)
COACH_INTERRUPT ──«Вернуть ход» (кнопка/голос)──▶ RETRY (ход снят; часы ребёнка = значение до хода; пуск после конца речи)
COACH_INTERRUPT ──«Оставлю так»──▶ BOT_THINKING (ошибка записана; бот её наказывает; тренер объясняет по факту)
RETRY ──ход──▶ JUDGING(retry): хорошо → конкретная похвала ▶ BOT_THINKING
                               та же/новая ошибка → следующая ступень подсказки (макс. 2 попытки на позицию) ▶ затем играем как есть
RETRY ──«Подскажи»──▶ следующая ступень лестницы, остаёмся в RETRY
```

Возврат — **предложение**, а не принуждение: у ребёнка остаётся право сказать «нет, я так хочу» (автономия; и обучение последствиями тоже работает). По умолчанию большая кнопка — «Вернуть ход».

| L4 | Bottom-out (ход) | «Лучше было слон на b3: слон уходит из-под боя и продолжает смотреть на f7» | «Конь f7! Вилка на ферзя и ладью» | стрелка лучшего хода; карточка в SRS с пометкой `revealed` |

Переход на следующую ступень: по просьбе ребёнка («подскажи»), после ~12–15 с молчания или после второй неверной попытки. Использованная ступень записывается в `InterventionRecord.maxHintLevel` и влияет на SRS-оценку и на статистику навыка.

### 4.5. Эскиз политики

```ts
export function decideIntervention(j: MoveJudgement, g: GameCtx, p: StudentProfile): InterventionDecision {
  const pol = POLICY[p.level.tier][g.timeControl.id];          // таблицы A и B
  const no = (reason: SuppressReason): InterventionDecision => ({ intervene: false, reason, logForReview: j.winPctLoss >= 10 });

  if (p.preferences.interventionMode === 'off' || g.mode === 'exam') return no('mode');
  if (!pol || pol.maxPerGame === 0)                         return no('timeControl');
  if (j.confidence !== 'confirmed')                         return no('lowConfidence');
  if (j.classification === 'book' || j.ply <= 4)            return no('opening');
  if (g.childClockMs < Math.max(30_000, 0.15 * g.timeControl.baseMs) || g.childClockMs < pol.minClockMs) return no('timeTrouble');
  if (g.interventionsUsed >= pol.maxPerGame - fadingPenalty(p, j.themes)) return no('budget');
  if (g.ply - g.lastInterventionPly < pol.cooldownPlies)    return no('cooldown');
  if (j.winPctBefore < 12 || j.winPctAfter > 88)            return no('notDecisive');
  if (g.themeInterventions(j.themes[0]) >= 2)               return no('letConsequencesTeach');

  const kind = j.classification === 'missedWin' ? 'missedWin' : 'blunder';
  const trig = pol.triggers[kind];
  const concrete = kind === 'blunder'
    ? (j.refutation?.mateIn ?? 99) <= trig.maxMateIn ||
      ((j.refutation?.materialSwing ?? 0) <= -trig.minMaterial && (j.refutation?.pliesToPunish ?? 99) <= trig.maxPlies)
    : (j.missed?.mateIn ?? 99) <= trig.maxMateIn ||
      ((j.missed?.materialGain ?? 0) >= trig.minMaterial && (j.missed?.plies ?? 99) <= trig.maxPlies);

  if (j.winPctLoss < trig.minWinPctLoss || !concrete)       return no('belowThreshold');
  if (j.explainability < pol.minExplainability)             return no('notExplainable');
  if (pol.letItGoProbability && g.rng() < pol.letItGoProbability && !isGameLosing(j)) return no('productiveFailure');

  return { intervene: true, kind, startHintLevel: 0, pauseClocks: true, restoreChildClockMs: j.clock.beforeMs };
}
```

## 5. Бюджет задержки для голоса

### 5.1. Факты о Realtime API (на 2026-09-21)

- Модели: `gpt-realtime` (снапшот `gpt-realtime-2025-08-28`, контекст 32k, max output 4096; текст $4 / $16, аудио $32 / $64 за 1M, кэш $0.40) — **семейство `gpt-realtime` (и `gpt-realtime-mini`) объявлено устаревшим 2026-07-20 и будет отключено 2027-01-20, рекомендованная замена — `gpt-realtime-2.1` / `-2.1-mini`; строить на нём нельзя** (developers.openai.com/api/docs/deprecations). Актуальные: **`gpt-realtime-2.1`** (контекст 128k, max output 32k; текст $4 / $24, аудио $32 / $64, кэш $0.40; картинки $5) и **`gpt-realtime-2.1-mini`** (контекст 128k, max output 32k; аудио $10 / $20, кэш аудио $0.30; текст $0.60 / $2.40, кэш $0.06; картинки $0.80 — по странице модели OpenAI). Эндпоинт обеих — только `v1/realtime`. В списке моделей OpenAI также есть `gpt-realtime-2`, `gpt-realtime-1.5` и новая **`gpt-live-1`** (см. 5.1a). У 2.x настраивается `reasoning.effort` (minimal / low / medium / high / xhigh — по гайду «Prompting Realtime models»; выше → больше задержка). Про значение по умолчанию источники расходятся: MarkTechPost пишет «low is the default», а гайд OpenAI советует «set reasoning effort to `low` instead of the default» — **задавать `low`/`minimal` явно, на дефолт не полагаться**. Поддержка function calling, prompt caching.
- Тарификация аудио (гайд «Cost optimization», `voice-latency-cost`): входное аудио = 1 токен / 100 мс (600 токенов/мин), выходное = 1 токен / 50 мс (1200 токенов/мин). Т. е. минута речи тренера на `gpt-realtime-2.1` ≈ $0.077, на mini ≈ $0.024; минута речи ребёнка ≈ $0.019 / $0.006 (плюс повторное чтение контекста по кэш-цене на каждом ходе диалога).
- Вставка контекста: `conversation.item.create` (в т. ч. system-сообщения посреди сессии), затем `response.create`. Чтобы модель заговорила первой — `response.create` без пользовательского ввода. Ответ «вне истории»: `response.create` с `conversation: "none"` (+ `metadata`, свой `input`).
- Function calling: вызов приходит в `response.done` (item типа `function_call` с `call_id`), результат возвращается item-ом `function_call_output` + `response.create`. Асинхронные вызовы поддержаны: модель может продолжать разговор, пока тул считает (в GA-релизе добавлены авто-плейсхолдеры, чтобы она не выдумывала результат).
- Перебивание: VAD отменяет ответ; для WebSocket — `conversation.item.truncate`; в WebRTC обрезка автоматическая. Сессия до 60 мин; `idle_timeout_ms`; усечение контекста настраивается (`truncation`, retention ratio 0.8 — реже сбрасывается кэш).
- Время до первого звука — не проверено (тема голосового исследования); ниже заложено 0.5–1.0 с как рабочая гипотеза.

### 5.1a. Альтернатива: `gpt-live-1` / Live API

Факты (developers.openai.com: страница модели, гайды `live`, `live-conversations`, `live-delegation`, `live-prompting`, `live-migration`, `voice-latency-cost`, `audio`):

- `gpt-live-1` — «full-duplex voice model… can listen and speak at the same time, and delegate reasoning and tool use to a backend agent». В API с **2026-09-10**. Эндпоинт только `v1/live/sessions` (WebRTC / WebSocket / SIP, плюс sideband-WebSocket для сервера). Страница «Audio and voice» начинается словами: *«For a new conversational voice application, start with GPT-Live»*; Realtime API — «когда нужен именно его session and tool model». Официального объявления об устаревании `gpt-realtime-2.1` **нет**.
- Цена: **$0.05 за минуту сессии**, посекундно, *включая тишину* (счётчик идёт, пока сессия открыта; советуют закрывать простаивающую сессию и восстанавливать контекст). Бэкенд-модель (если есть) тарифицируется отдельно. Контекст 128k; при 90 % — автоматическая замена «голосового движка» с ≤ 8 192 токенами сжатой истории. `instructions` до 16 384 токенов.
- Два режима делегирования: **Responses delegation** (OpenAI сам вызывает выбранную Responses-модель, рекомендуют GPT-5.6 Terra / Luna; наши function tools всё равно исполняем мы) и **client delegation** (по умолчанию, если `delegation` не задан): приходит `session.delegation.created` (без текста запроса — его надо брать из `session.input_transcript.delta`), приложение само считает ответ и возвращает его.
- Управление речью из приложения — три события, каждое ≤ 500 токенов, с обязательным полем `delegation_id` (можно `null`): `session.commentary.append` — «information the model should speak aloud, **paraphrasing** the appended text»; `session.thinking.append` — факты «для внутреннего рассуждения», вслух не произносятся, но доступны для следующих ответов; `session.instructions.append` — системные указания (поздороваться первым, замолчать и т. п.). Микрофон: `session.input_audio.mute` / `unmute`. Транскрипты: `session.input_transcript.delta` / `session.output_transcript.delta` (с `start_ms`/`end_ms`). События «конец реплики» **нет** — воспроизведение отслеживает клиент.
- Голоса: по умолчанию `marin` + 12 новых (Quartz, Ripple, Vesper, Willow, Stone, Gleam, Meridian, Bossa, Tempo, Beacon, Delta, Cinder) — все с английской или бразильско-португальской «региональной окраской»; голос нельзя сменить внутри сессии; есть custom voices. **Русского «родного» голоса в таблице нет**; документация говорит лишь «test the voice with the languages… your application needs». Качество русского и детской подачи — не проверено.

Соответствие нашей архитектуре (Realtime → Live):

| Наш механизм | Realtime API (`gpt-realtime-2.1`) | Live API (`gpt-live-1`) |
|---|---|---|
| `CoachEvent` с `talkingPoints`, тренер должен сказать | `conversation.item.create` + `response.create` | `session.commentary.append` (`delegation_id: null`) |
| `state_sync` («знай, но молчи») | `conversation.item.create` без `response.create`; чистка через `conversation.item.delete` | `session.thinking.append`; события удаления среди клиентских событий гайда нет — «GPT-Live manages context automatically» |
| Вопрос ребёнка → локальные факты | function tools (`explain_move`, `get_hint` …), вызов в `response.done` | client delegation: `session.delegation.created` → наш код/движок → `commentary.append` с тем же `delegation_id` |
| Запреты / смена режима | `session.update` (instructions) | `session.instructions.append` |
| Перебивание, «угу», одновременная речь | VAD + отмена ответа, полудуплекс | нативно, полный дуплекс |
| Вне-диалоговые ответы (`conversation: "none"`), текстовый вывод, push-to-talk | есть | прямого аналога в гайдах не найдено |

Оценка стоимости часа игры (прикидка, **не измерено**): тренер говорит ~6 мин/ч, ребёнок ~3 мин/ч, ~60 событий по 400 токенов. `gpt-realtime-2.1` ≈ $0.6–1.5/ч, `-mini` ≈ $0.2–0.5/ч; `gpt-live-1` ≈ **$3.0/ч** при постоянно открытой сессии (меньше, если закрывать сессию в долгих паузах, но тогда теряется «всегда слушает»). То есть Live дороже в нашем «малоразговорчивом» сценарии, зато даёт именно целевой UX («слушает и говорит одновременно»), и снимает с нас логику VAD/перебиваний.

Рекомендация: не выбирать вслепую. Весь голосовой слой — за интерфейсом `VoiceTransport { say(talkingPoints), remember(facts), onChildQuestion(cb), mute(), close() }` с двумя реализациями; на этапе 5 (раздел 8) прогнать один и тот же мини-eval из 50 событий на русском на `gpt-live-1`, `gpt-realtime-2.1` и `-mini` (нарушения белого списка, естественность русского, задержка, цена). Пост-валидатор транскрипта нужен в обоих случаях: Live по документации **пересказывает**, а не зачитывает текст дословно. Модель вышла в API только 2026-09-10 — закладывать риск сырости API.

### 5.2. Кто что делает и когда

| Слой | Когда | Содержимое | Бюджет |
|---|---|---|---|
| **Предрасчёт** (пока ребёнок думает) | после каждого хода бота | глубокий MultiPV=3 по P0; null-move угрозы; PositionFacts(P0); мотивы лучшего хода; заготовки подсказок L1–L4; «за что похвалить, если найдёт лучший» | без ограничений (секунды) |
| **Быстрая проверка** | t = 0…600 мс после хода | кэш MultiPV → либо quick 250 мс → confirm 350 мс; causes, explainability, решение | ≤ 600 мс, скрыто паузой бота |
| **Локальная мгновенная реакция** | t ≈ 600 мс | анимация маскота + **заранее записанный клип** тем же голосом («Стой-стой!», «Ого!», «Хм…») — 0 сети | 0 мс сети |
| **Push в realtime** | одновременно с клипом | `CoachEvent` (≤ 300–400 токенов): тип, 1–3 `talkingPoints`, `mentionable`, запреты (например, «не называй лучший ход»), лимит длины реплики; затем `response.create` | первый звук модели ≈ через 0.5–1.0 с → стыкуется с концом клипа (~1.2 с) |
| **Тулы realtime-модели** (pull) | когда ребёнок спрашивает голосом | см. 5.3; все локальные, ответ < 300 мс (движковые — movetime 200–300) | < 300 мс + задержка модели |
| **Офлайн-мозг** (текстовая модель) | после партии / ночью | разбор, журнал, план; без ограничений по задержке; через `codex exec` на подписке | секунды–минуты |

Правила экономии и свежести контекста:

- Сессионные `instructions` — статичны (персона, правила безопасности, правило «говори только то, что в фактах») → попадают в кэш.
- Состояние доски **не шлём на каждый ход**. Храним последний `state_sync` на нашей стороне; при `input_audio_buffer.speech_started` (ребёнок заговорил) сразу вставляем свежий `state_sync`, а автоответ VAD отключаем (`create_response: false`) и шлём `response.create` сами — так модель гарантированно отвечает по актуальной позиции.
- Устаревшие `state_sync` удаляем (`conversation.item.delete`), чтобы контекст не рос и модель не путала позиции.
- Молчаливые события (обычный хороший ход) в модель не отправляются вовсе: `speakPolicy: 'silent'`.

| `save_child_thought({text})` | ok | мысли ребёнка вслух → журнал (привязка к ply) |
| `get_student_note({topic})` | краткая выжимка из StudentProfile | «ты уже 3 раза на этой неделе находил вилки!» |

Сырые сантипешки модели не выдаём — только словесные градации («у тебя большое преимущество»), иначе она начнёт их озвучивать ребёнку.

### 5.4. Защита от галлюцинаций (сводно)

1. Модель никогда не вычисляет шахматы — только озвучивает `talkingPoints` и результаты тулов.
2. Белый список `mentionable` в каждом событии + системное правило «не называй ходы, поля и фигуры, которых нет в событии/ответе тула; если не знаешь — вызови тул или скажи "давай проверим"».
3. **Пост-валидатор транскрипта**: из `response.output_audio_transcript.done` извлекаются упоминания фигур/полей/ходов (русские названия + координаты), сверяются с доской и белым списком → метрика `hallucinationRate`; при нарушении в критической реплике — корректирующее событие («Ой, я оговорился: …») и визуальная правда на доске. Это тот же приём «атомарные утверждения → детерминированная проверка», что в ACT-Eval.
4. Консервативные детекторы мотивов (точность важнее полноты); юнит-тесты на размеченной базе пазлов lichess (темы пазлов — готовая разметка; цель precision ≥ 95 % по каждой теме).
5. Офлайн-тексты: JSON Schema → валидация каждого SAN на легальность в указанном FEN → до 2 перегенераций → fallback на шаблон.
6. `confidence` влияет на тон; вмешательство только при `'confirmed'`.

## 6. Разбор после партии и долгосрочная модель ученика

### 6.1. Пайплайн разбора (офлайн)

1. **Глубокий анализ** всей партии: judge engine, depth 18–22 или 0.5–1 с/ход, MultiPV=2 → окончательные `MoveJudgement[]` (заменяют «быстрые»); точность партии по формуле lichess; точность по фазам.
2. **Выбор ключевых моментов**: не более **3** для ребёнка (внимание!), ранжирование `score = winPctLoss × explainability × новизна/актуальность темы для профиля`; обязательно ≥ 1 положительный момент (great / brilliant / лучший найденный ход / удачная вторая попытка после возврата).
3. **ReviewPacket (JSON)**: метаданные партии, ключевые моменты с PositionFacts и talkingPoints, сводка по темам, выдержка из StudentProfile, последние N уроков (чтобы не повторяться — приём Arrakis).
4. **Текстовая модель** через подписку: `codex exec --skip-git-repo-check --ephemeral -s read-only --output-schema review.schema.json --json -o out.json -` (все флаги есть в codex-cli 0.154.0 — проверено `codex exec --help`). Выход: `kidStory` (2–3 абзаца), `keyLesson` (одна мысль), `practiceFocus`, `parentNotes` (технически, с цифрами), `journalMarkdown`. Подробности: (1) `--output-schema` официально документирован (learn.chatgpt.com/docs/non-interactive-mode, раздел «Create structured outputs with a schema»); то же даёт `@openai/codex-sdk`: `thread.run(prompt, { outputSchema })`. (2) Обязательно добавить `-m gpt-5.6-luna` (или `gpt-5.6-terra`) `-c model_reasoning_effort="low" --ignore-user-config`: иначе наследуется пользовательский дефолт (например, `gpt-6-astra` / effort `ultra`). (3) Лимиты (страница цен Codex, оценки «локальных сообщений за 5 часов», тариф Plus): GPT-6 Astra 5–45, GPT-5.6 Sol 10–100, **GPT-5.6 Terra 25–200, GPT-5.6 Luna 250–2 000**; есть ещё недельный лимит; квота общая со всей остальной работой в Codex/ChatGPT. (4) Пробный запрос с этими флагами CLI разобрал без ошибок, но отклонил с `You've hit your usage limit … try again at …` — сценарий «подписка исчерпана на несколько суток» реален. Разбор должен ставиться в очередь и автоматически уходить в fallback. Допустимость «не-кодового» трафика по условиям использования — не проверено (документация описывает Luna как модель для «classification, extraction, support, background automation», прямого запрета не найдено). Fallback — Responses API по ключу (`CODEX_API_KEY=… codex exec` или напрямую SDK `openai`).
5. **Валидация**: каждый упомянутый ход/поле проверяется по пакету; при ошибке — перегенерация, затем шаблон.
6. **Артефакты**: PGN с комментариями, NAG (`$2` mistake, `$4` blunder, `$6` inaccuracy, `$1`/`$3` хорошие) и `[%eval …]`/`[%clk …]`; markdown-журнал (мысли ребёнка вслух с привязкой к ходам, вмешательства, подсказки, итог); обновление StudentProfile; новые SRS-карточки.
7. **Голосовой дебриф**: realtime-сессия получает уже провалидированный сценарий разбора (3 момента) и ведёт по нему диалог, показывая позиции через `show_on_board`.

### 6.2. Модель ученика

- **Темы** = темы пазлов lichess (тактика) + свои: дебютные принципы (`opening:development`, `opening:center`, `opening:castle`, `opening:queenEarly`, `opening:samePieceTwice`), эндшпильная техника (`endgame:KQK`, `endgame:KRK`, `endgame:squareRule`, `endgame:opposition` …), привычки (`habit:impulsive`, `habit:timeTrouble`, `habit:checksCapturesThreats`).
- По каждой тактической теме **две стороны**: `asAttacker` (была возможность — нашёл/не нашёл) и `asDefender` (соперник угрожал — отразил/зевнул). У новичков это разные навыки, и второй важнее.
- Счётчик: `opportunities`, `successes`, экспоненциальное среднее (полураспад ~20 эпизодов), `lastSeen`, тренд; статус `unknown → weak → developing → solid → mastered` (по EWMA и числу наблюдений; для `mastered` нужно ≥ 15 эпизодов и EWMA ≥ 0.85).
- Оси «как у Aimchess» для родителя: тактика, эндшпиль, реализация перевеса (партии, где было > 80 % и не выиграл), упорство в защите, время, дебют.
- Привычки: доля зевков, сделанных быстрее 3 с; доля зевков при < 30 с на часах; успешность второй попытки после возврата; средняя использованная ступень подсказки (должна падать).
- «Память тренера»: последние уроки, что хвалили, повторяющиеся советы, цитаты мыслей ребёнка — короткая выжимка (≤ 150 токенов) кладётся в событие `game_start`.
- Эскалация (приём Arrakis): тема — в топе слабостей в ≥ 3 разных партиях за 2 недели → тренер назначает мини-урок/серию пазлов по теме из учебного плана.

### 6.3. Очередь интервального повторения из собственных ошибок

- **Отбор**: `winPctLoss ≥ 10` (или missedWin); решение достаточно однозначно (вторая линия хуже лучшей на ≥ 14 п. Win% — зеркало `areSimilarEvals` lichess); позиция не безнадёжна; подтверждено глубиной ≥ 18; `explainability ≥ 1`.
- **Типы карточек**: `findBest` (найди лучший ход — классика «learn from your mistakes»); `blunderCheck` (показан ход, который ребёнок сделал в партии: «этот ход безопасен?» — собственная вариация Aimchess Blunder Preventer, где выбирают из двух ходов; тренирует именно защитный навык); `punish` (соперник ошибся — накажи; из missedWin); позже — `convert` (доиграй выигранную позицию против бота).
- **Зачёт ответа**: ход движка, либо любой ход с потерей < 4 п. Win% (критерий lichess retro), либо мат.
- **Планировщик**: `ts-fsrs` 5.4.2 (MIT), `request_retention` ≈ 0.9. Оценка: без подсказок с первой попытки → Good (быстро — Easy); с подсказкой L1–L2 или со второй попытки → Hard; L3–L4 или провал → Again.
- **Дозировка**: 5–8 карточек в день перед игрой («разминка»), собственные ошибки разбавляются пазлами lichess той же темы и подходящего рейтинга (база пазлов lichess открыта под CC0 — не проверено, тема учебного плана).

  source: 'nullMove' | 'pv'; phraseRu: string;
}

}

}

}

export interface MoveJudgement {
  gameId: string; ply: number; moveNumber: number; color: Color; byChild: boolean;
  move: SpokenMove; fenBefore: Fen; fenAfter: Fen;
  evalBefore: Score; evalAfter: Score;           // POV сходившего
  winPctBefore: number; winPctAfter: number; winPctLoss: number; cpLoss: number | null; accuracy: number;

  confidence: 'quick' | 'confirmed' | 'deep';
  clock: { beforeMs: number; afterMs: number; spentMs: number };
  childThought?: string;                         // расшифровка мыслей вслух на этом ходу

## 8. Порядок реализации (минимальный путь)

1. `winPct` / `classify` / точность (порт из lila + Chesskit) + юнит-тесты на контрольных значениях из раздела 2.1.
2. Judge engine: нативный Stockfish 19 по UCI, режим ponder MultiPV=3, quick/confirm; **замер глубины за 250/600 мс на целевом Mac**.
3. PositionFacts v1: материал, hanging/SEE, связки, null-move угрозы, маты в 1–3, вилка, слабость последней горизонтали → `causes` + `explainability`. Тесты на пазлах lichess по темам.
4. Машина состояний возврата хода + политика (таблицы A–D) + часы. Сначала с текстовыми репликами из шаблонов, **без LLM** — система должна быть полезной и правдивой уже на этом шаге.
5. Голосовой слой за интерфейсом `VoiceTransport`: `CoachEvent` → голос; тулы / client delegation; пост-валидатор транскрипта; локальные клипы. Две реализации (`gpt-realtime-2.1[-mini]` через `v1/realtime` и `gpt-live-1` через `v1/live/sessions`) и сравнительный мини-eval на русском (см. 5.1a).
6. Послепартийный разбор через `codex exec` + PGN/markdown + StudentProfile + SRS.
7. Расширение детекторов мотивов, дебютные принципы, эндшпильные темы, fading.

## 9. Риски

- Ложные «стоп» из-за мелкой глубины быстрой проверки → потеря доверия ребёнка. Смягчение: confirm-поиск, материальная конкретика, правило `confidence === 'confirmed'`.
- Realtime-модель всё равно может оговориться в названии поля/фигуры (у CCC даже с заземлением 20 % ошибок, у GPT-5.4 с тулами 9 %). Смягчение: talkingPoints, белый список, пост-валидатор, «истина на доске» стрелками от кода.
- Лицензии: Stockfish GPL-3.0, chessops GPL-3.0-or-later, lichess-puzzler / lila / Chesskit / Arrakis — AGPL-3.0. Порт `cook.py` делает код производным от AGPL. Для семейного локального приложения это не проблема; при публичном распространении/хостинге — нужно либо открывать код, либо писать детекторы с нуля и держать движок отдельным процессом.
- Зависимость от подсказок («костыль»). Смягчение: бюджеты, fading, `letConsequencesTeach`, режим «Экзамен».
- Стоимость realtime при постоянно открытом микрофоне: ставки известны (600 / 1200 аудио-токенов в минуту вход / выход; `gpt-live-1` — $0.05/мин сессии, см. 5.1 и 5.1a), фактический расход на партию — не измерен; вероятно потребуется локальный VAD/push-to-talk и агрессивное усечение контекста (для Realtime) либо закрытие простаивающей сессии (для Live).
- `codex exec` как бэкенд не-кодовых задач: лимиты известны (см. 6.1), но квота общая с остальной работой в Codex и **может быть исчерпана на несколько суток**; fallback на API обязателен, модель и effort задавать явно.
- Выбор голосового API: `gpt-live-1` вышла в API 2026-09-10 и рекомендована OpenAI для новых голосовых приложений, но API совсем новый, русских голосов в таблице нет, текст она пересказывает, а не зачитывает; `gpt-realtime-2.1` зрелее и дешевле в нашем сценарии. Старое семейство `gpt-realtime` отключается 2027-01-20. Смягчение: интерфейс `VoiceTransport`, сравнительный мини-eval.
- Win%-кривая lichess откалибрована на 2300+; для новичка завышает «цену» небольших потерь. Смягчение: материальный критерий и explainability; `K` вынести в конфиг.

## 10. Открытые вопросы

1. Реальная глубина/nps нативного Stockfish 19 на M5 Max за 250 и 600 мс, в т. ч. при MultiPV=3 (заметно замедляет набор глубины по главной линии), и WASM-варианта, если UI-only — измерить; «14–17 полуходов» из 4.2 — гипотеза.
2. Фактическое время до первого звука у `gpt-realtime-2.1` vs `-mini` vs **`gpt-live-1`** на русском и качество детского/молодого голоса (у Live — без «родного» русского голоса в таблице; сведения о «языковых тирах» GPT-Live, где русский — «Tier 2», есть только на стороннем gptlives.com, анонс openai.com/index/introducing-gpt-live-1-in-the-api/ отдаёт 403) — в голосовом исследовании.
3. Насколько надёжно realtime-модель следует правилу «говори только talkingPoints» на русском — нужен мини-eval (50 событий, пост-валидатор считает нарушения).
4. Допустимо ли по условиям использования гонять через `codex exec` / `@openai/codex-sdk` на подписке ChatGPT разборы партий (лимиты известны, см. 6.1; открыт только вопрос условий); политика OpenAI в отношении приложений для детей младше 13 лет.
5. Использует ли Chess.com в Play Coach LLM или шаблоны; есть ли там часы — не раскрыто.
6. Нужна ли пауза часов при спонтанном вопросе ребёнка в 5-минутке (предложено: ответ ≤ 5 с без паузы, дольше — предложить паузу).
7. Оценка Elo ребёнка для выбора Tier: по результатам с ботами известной силы или по рейтингу пазлов — согласовать с исследованием по ботам.
8. Реальная стоимость часа игры для каждого голосового варианта (в 5.1a — прикидка); тарифицируется ли Live-сессия при `session.input_audio.mute` (по смыслу документации — да, счётчик идёт до `session.close`).
9. Есть ли в Live API аналоги `conversation: "none"`, текстового вывода и удаления элементов контекста (в гайдах не найдено; полный API reference не прочитан).
10. Precision порта детекторов `cook.py` на PV движка: в оригинале детекторы рассчитаны на структуру пазла (решающая сторона ходит на нечётных полуходах, линия выигрывает), на произвольных PV возможны ложные срабатывания — нужна собственная валидация (5.4 п. 4).
11. Не перепроверялись по первоисточнику (на архитектуру не влияют): значения CCC 0.60 и 0.20 / 0.46, детали Dr. Wolf, ChessKid, Magnus Trainer, Chessvia, DecodeChess, ElevenLabs-голоса Chess.com, Maia-2/3, LAK'26.
